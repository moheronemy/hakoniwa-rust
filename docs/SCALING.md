# 大規模化の設計

Perl 版の規模 (30 島・12×12・6 時間ごと) を大きく超えて動かすための設計。
ゲームのルール (`hakoniwa-core` のターン処理と操作) は変えず、その周りを組み替える。

## 目標

| 項目 | 上限 |
|---|---|
| 島の数 | 1000 |
| 地図の大きさ | 128×128 (1 島 16,384 マス、全体で約 1,640 万マス) |
| ターンの間隔 | 数十秒 |

## 現状の計測

release ビルド、1 コアで計測。「全面」はテスト用の開発済みの島 (`phase4-mix-1`) の 12×12 の地図を
128×128 に敷き詰めたもの (最悪の場合の見積もり)、「中央」は 128×128 の中央に 12×12 を置き、残りを海にしたもの。

| 条件 | 1 ターン | 1 ターンのログ | JSON 全体 | 全体の複製 / JSON 書き出し |
|---|---|---|---|---|
| 1000 島・12×12 (開発済み) | 0.14 秒 | — | 21 MB | 5 ms / 13 ms |
| 1000 島・128×128 中央 | 約 2 秒 | 6.8 万件 | 362 MB | 0.16 秒 / 0.74 秒 |
| 1000 島・128×128 全面 | 5〜9 秒 | 400 万件 | 1.2 GB | 0.68 秒 / 1.95 秒 |

ログの大半は施設ごとの収入のログ (金山・温泉街・天然スケート場から「○億円の収益」など) で、
開発済みのマスの数に比例する。

### 負荷テスト (`scale_bench`)

突き合わせ用のデータの島を複製して、目標の規模でターン処理を測る。
`--max-turn-secs` を超えたターンがあれば終了コード 1 で失敗する。

```sh
cargo run --release -p hakoniwa-core --example scale_bench -- \
    --fixture size-128-1 --islands 1000 --turns 3 --max-turn-secs 10
```

`--save PATH` を付けると、作った状態を `state.json` の形で保存する。サーバーを目標の規模で動かして確かめるときに使う。
`--persist DIR` を付けると、データディレクトリへの保存 (スナップショット・操作の差分・読み込み) の時間と大きさも測る。

データは `tools/fixtures/scale_size.py` で作る、Perl 版と突き合わせ済みの 128×128 の島
(全地形・全種類の計画・政策をばらまいたもの)。手順 1 の時点の結果 (release、1 コア):

| データ | 1 ターン (3 ターン) | 1 ターンのログ | 状態の複製 | JSON 全体 / 書き出し |
|---|---|---|---|---|
| `size-128-1` (3/4 が陸) × 1000 島 | 13.3 / 10.2 / 10.0 秒 | 277 万 / 137 万 / 107 万件 | 0.87 秒 | 1.5 GB / 2.2 秒 |
| `size-128-2` (6 割が海) × 1000 島 | 7.0 / 5.9 / 6.3 秒 | 129 万 / 60 万 / 48 万件 | 0.45 秒 | 0.9 GB / 1.3 秒 |

`size-128-1` は最悪の場合に近い (全マスに施設や怪獣がある)。ターンの間隔を 30 秒とすると、
1 ターンは間隔の 1/3 (10 秒) 以内に収めたいので、手順 5 (core の高速化) が要る見込み。

## 変えられないこと

ターン処理は島ごとに並列にできない。Perl 版のルールは

- 1 本の乱数の並びを島の順に使う
- グローバル変数が島をまたいで残る (`PORTING.md` の「Perl 版の挙動をそのまま再現しているもの」)
- ミサイル・援助・怪獣派遣などで島どうしが影響し合う

ので、並列にすると結果が変わる。ターン処理は `run_turn` (純粋な関数) のまま 1 本で動かし、
1 コアの速さで目標の間隔に収める。

## いまの構成で成り立たないところ

1. **保存**: 操作 1 件・ターン 1 回ごとに `GameState` 全体を複製し、JSON 全体を書き直す (`hakoniwa-server/src/edit.rs`, `turns.rs`)。
   目標の規模では 1 回 1.2 GB  
   (手順 3 で解消)
2. **ロック**: ターン処理と保存のあいだ書き込みロックを持つので、画面も操作も最大 10 秒ほど止まる。
   保存は非同期の中で同期の `std::fs` を使い、tokio のワーカーを塞ぐ  
   (手順 2 で解消: 読み取りは止まらず、保存は別のスレッドで行う)
3. **ログ**: `GameState::logs` に HTML の文面で持ち、保存のたびに書かれる。400 万件 × 保存するターン数になる (手順 3 で解消)
4. **画面**: 地図を HTML の表で出している。1 枚 16,384 マス

## 設計

### 1. 状態のスナップショットと、止まらない読み取り

手順 2 で実装した (`hakoniwa-server/src/store.rs`)。

- 状態は `Arc<GameState>` のスナップショットで公開する。画面はそれを受け取るだけで、ロックを待たない
  (差し替えのための `std::sync::RwLock<Arc<_>>` はポインタを取り出すあいだしか持たない)
- 書き込み (画面の操作・ターン処理・管理画面) は公平な `tokio::sync::Mutex` の順番待ちに並ぶ。
  ターン処理中に来た操作はターンが終わってから順に行われる (Perl 版でもターン中の入力はターンのあとに効く)。
  乱数は書き込む側だけが使うので、この順番待ちの中に持つ
- 書き込む側は今の状態を複製して書き換え、保存できたときだけ公開する。ターン処理と保存は `spawn_blocking` で行う
- 複製を安くするため、core の地図のマス (`IslandMap::cells`) と済んだターンのログ (`Logs::turns`) を
  `Arc` で共有し、書き換えるときだけ写す (`Arc::make_mut`)。保存の形 (JSON) は変わらない。
  当初の案の `Arc<Island>` より変更が小さく、複製の時間は同じく無視できるほどになった

結果 (1000 島・128×128 の `size-128-2`、手順 2 の時点):

| | 手順 2 の前 | 手順 2 のあと |
|---|---|---|
| 状態の複製 | 0.87 秒 | 0.006 秒 |
| ターン処理と保存 (13 秒ほど) のあいだのトップページ | 12.7 秒待たされた | 0.1 秒おきに 122 回読み、最大 34 ms |
| 1 ターン (`scale_bench`) | 7.0 / 5.9 / 6.3 秒 | 7.4 / 6.5 / 6.8 秒 |

1 ターンが 5% ほど遅くなったのは、マスを書き換えるたびに共有を確かめる (`Arc::make_mut`) ためと思われる。
手順 5 で計測して見直す。ターン処理のあいだは、書き換えた島の地図が前のスナップショットと新しい状態の
2 つ分メモリに載る (128×128 の島 1 つで約 260 KB)。

画面の操作は、以前と同じく時刻が来ているターンを先に進めない (ターンは定時実行が進める。島の登録だけは先に進める)。

### 2. 保存: スナップショットと操作の差分

手順 3 で実装した (`hakoniwa-core/src/persist.rs`)。当初の案 (操作の入力と乱数の種を記録し、
起動時にゲームのルールを動かしてなぞる) は、移植版を新しい版にしたときになぞった結果が変わりうるので、
**変わったあとのデータ**を記録する形にした。また計測の結果、ログを除いた状態全体はバイナリ + 圧縮で
小さく速い (下の表) ので、スナップショットはターンごとに書く。

データディレクトリ (`data_dir`、省略時は `state_path` と同じ場所の `store`):

| ファイル | 中身 | 書くとき |
|---|---|---|
| `snapshot.bin` | 見出し (世代・ターン・最終更新時刻・島の数・ログの番号) + 状態 (ターンのログを除く) を bincode + zstd | ターンのたび (一時ファイル + rename) |
| `journal-<世代>.bin` | 画面の操作 1 件ごとの差分: 全体の値と、変わった島 (地図は変わったときだけ) | 操作のたびに追記して fsync |
| `logs/<番号>.bin` | 1 ターン分のログ (`TurnLog`) | ターンのたび。一度書いたら変えない |
| `backup<N>/` | バックアップ (`snapshot.bin` と `logs/`。ログはハードリンク) | `$HbackupTurn` ターンおき (ターンの前の状態) |

- 起動するときは、スナップショットに同じ世代の差分を順に当てる。最後の 1 件が書きかけなら捨てて切り詰める。
  記録はデータなので、読み直すときにゲームのルールは動かさない
- スナップショットを書いたら世代を進め、古い差分とどこからも指されないログを消す
- 乱数はこれまでどおりサーバーに 1 本 (記録しない)
- JSON の `state.json` は移行の入口として残す。データディレクトリが無ければ起動時に読み込む。
  `hakoniwa-server --export-json PATH` で JSON に書き出せる (中身の確認、形式の版 `persist::FORMAT` が変わったとき)

結果 (1000 島・128×128、`scale_bench --persist`。`size-128-1`):

| | JSON 1 ファイル | データディレクトリ |
|---|---|---|
| ターンごとの保存 | 2.2〜4.7 秒 (1.5 GB) | 0.46 秒 |
| 画面の操作 1 件の保存 | 全体の書き直し | 中央 4.6 ms、最大 5.6 ms |
| 起動時の読み込み | — | 0.46 秒 (スナップショット + 差分 20 件) |
| ディスク | 1.5 GB | 82 MB (ログ 5 ターン分を含む) |

サーバーで確かめた結果 (`size-128-2`): JSON (1.3 GB) からの移行を含む最初の起動 2.9 秒、2 回目からの起動 0.42 秒。
ターンの要求 (ターン処理 + 保存) は 13.4 秒から 8.4 秒になった。

### 3. ログの圧縮と別保管

手順 3 で実装した (`hakoniwa-core/src/turn_log.rs`)。1 ターンのログは最大 277 万行・本文 392 MB になり、
メモリにも数ターン分は持てない。

- 1 ターン分を `TurnLog` にする: 行の並びのまま 1024 行ずつ bincode + zstd で圧縮したかたまりと、
  「島 ID → その島が関わる行を含むかたまり」の索引。圧縮は CPU の数だけ並べて行う
- 島の近況は、索引にあるかたまりだけを展開する。全部の行は順に展開する
- 行の文面は Perl 版と同じ HTML のまま。JSON では今までどおり行の並びとして読み書きするので、
  Perl 版との突き合わせテストは変わらない
- ログのファイルは 1 ターン 1 つ (`logs/<番号>.bin`)。スナップショットには入れない

当初の案の「出来事の種類と値で持ち、文面は表示のときに作る」は、281 個のログの関数をすべて書き換えることになる。
圧縮で大きさの問題は解けた (5 ターン分で約 1 GB → 65 MB) ので見送った。
ターン処理は圧縮のぶん 0.5〜0.9 秒長くなる (`size-128-1`)。

残った問題: トップページと最近の出来事は、全部の島のログを 1 ページに出す。目標の規模では 1 ターン分で
129 万行・140 MB の HTML になり、2.3 秒かかる (島のページは 57 ms)。手順 4 でページ送りにする。

### 4. 画面

- 地図は JSON かバイナリで送り、ブラウザの canvas で描く。見えている範囲だけ送る
- トップページは島の一覧をページ送りにし、スナップショットごとにキャッシュする (ETag)

### 5. core の高速化 (必要なら)

計測してから行う。候補はターン中のログの文面づくり (3 で不要になる) と、マスのデータの大きさ
(`LandCell` はいま 16 バイト)。どれも Perl 版との突き合わせテストがすべて通ることを条件にする。

## 確かめ方

- **大きな地図での一致**: Perl 版の `$HislandSize` を変えて動かし、移植版と突き合わせる (手順 1 で済み)。
  - 段階ごと: `size-13-1`, `size-32-1`, `size-128-1`, `size-128-2` (`tools/fixtures/scale_size.py`)。
    データのディレクトリに `island_size` のファイルを置くと、`run-harness.sh` は `$HislandSize` を
    書き換えて動かし、`perl_compat_tests` はその大きさで読み込む
  - ターン全体: `cgi/turn-size-32`, `cgi/turn-size-128` (`run_cgi_settings.py` の
    `"perl_settings": {"HislandSize": "128"}`。`full_turn_tests` もこれを読む)
  - どれも一致した (移植版に地図の大きさを 12 と決め打ちして結果が変わる箇所は見つからなかった)
- **負荷テスト**: 目標の規模のデータでターン処理を測り、決めた時間を超えたら失敗するようにする
- 1〜4 は core の外の変更なので、既存の突き合わせテストがそのまま基準になる

ゲームの釣り合い (地図が 100 倍以上になったときの人口・収入・災害) はルールの問題で、この設計では扱わない。
